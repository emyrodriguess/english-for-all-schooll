## Design Specificity Verdict

The operational model is clearly authored for English For All: recurring availability, contracts, invoices, receipts and pedagogical history all fit the school workflow. The presentation is only moderately product-specific: it uses a disciplined, generic backoffice language instead of making availability, risk, and next actions immediately legible.

The deterministic scan of `app/admin` returned zero findings. That is a clean mechanical result, not evidence that the experience is complete. Browser access reached only `/admin/login`, because protected routes redirected without an authenticated session; the login visual is calm and well structured. No overlay could be injected because the available browser surface only supports read-only evaluation.

## Overall Impression

The foundation is trustworthy and more coherent than a typical MVP. The central opportunity is to make the application more operationally decisive: expose the answer before the user has to drill down, preserve navigation intent, and protect readability over artificial density.

## What's Working

1. Dialog microcopy explains historical consequences before destructive actions.
2. The student detail page gathers contract, finance, planner, and classes around the user’s real entity.
3. The shared shell, badges, empty states, and filters establish a disciplined visual system.

## Priority Issues

### [P1] Financial navigation from a student row does not honor the request

`StudentTable` links to `?tab=financeiro`, but the student page initializes the overview tab. Read and validate the URL tab, then make tab changes update the URL. This preserves a direct investigation flow and browser navigation.

### [P1] Agenda conceals the answer the user opens it to find

Every weekday starts collapsed with no available/occupied summary. Show counts in each accordion trigger and open the current or filtered day by default. Details can remain progressive, but availability must be scannable.

### [P1] Searchable entity selection is incomplete for keyboard and assistive technology

The custom combobox exposes combobox/listbox roles without arrow navigation, active option state, or `aria-activedescendant`. Use an established accessible primitive or fully implement roving focus, Home/End, result count announcements, and active-descendant semantics.

### [P2] Density is being achieved by shrinking operational text

Several recurring data and helper styles are 0.58–0.75rem. Raise data text to at least 0.8125rem and auxiliary text to 0.75rem; retain density through hierarchy and progressive disclosure rather than smaller type.

### [P2] Group-class planner entry will not scale with real class size

The class registration dialog shows several general fields plus three fields for each active student. Stage the general record first and reveal individual notes as collapsible rows or a second step with a fast “no individual note” path.

## Persona Red Flags

### Alex — experienced administrator

Finding an open time requires opening several days; repeated payment and scheduling actions have no accelerator, keyboard shortcut, or batch path.

### Sam — keyboard or assistive-technology user

The custom combobox lacks expected keyboard navigation, operational text can fall below comfortable reading size, and an English-only screen-reader close label is inconsistent with the Portuguese interface.

### Casey — interrupted mobile user

The responsive shell and horizontal table scrolling follow the product guidance, but critical actions can move far across a wide table and smaller controls/text reduce comfortable one-handed use.

## Minor Observations

- `loading.tsx` returns no visible feedback; a shell/content skeleton would maintain perceived responsiveness.
- Use weekday names instead of `Dia 1`, or expose both.
- Separate finance outbox status from an action so “no message today” cannot imply manual sending.
